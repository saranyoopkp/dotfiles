# Compatibility & Rollout (N / N-1 compatibility)

ตอน deploy ระบบที่ยังทำงานอยู่ **ของเก่ากับของใหม่อยู่ด้วยกันเสมอชั่วขณะ** —
rolling deploy, client ที่ยังไม่รีเฟรช, message ที่ค้างในคิว, mobile app ที่ user ยังไม่อัปเดต
บั๊กหมวดนี้ **มักไม่ error แต่ตายเงียบ** และโผล่ตอน*คนอื่น* deploy ไม่ใช่ตอนเราเขียน

## กฎเดียว
**ของใหม่ต้องเข้ากันได้กับของเก่า และของเก่าต้องไม่พังเพราะของใหม่**
ทำได้ = **ลำดับการปล่อยไม่สำคัญ** → ไม่ต้องมานั่งเรียงว่าอะไรขึ้นก่อน (ซึ่งเป็นสิ่งที่คนจะลืม)

## Expand → Migrate → Contract
- **เพิ่มของใหม่** (field/endpoint/column/event type) → ปลอดภัยเสมอ ทำได้เลย
- **ลบ / เปลี่ยนชื่อ / เปลี่ยนความหมาย** → 🔴 **แบ่ง 2 รอบเสมอ ไม่มีข้อยกเว้น**
  1. `expand` — เพิ่มของใหม่ + เขียนทั้งเก่าและใหม่ + อ่านจากใหม่ (ของเก่ายังอยู่)
  2. `contract` — ลบของเก่า เมื่อแน่ใจว่าไม่มีใครใช้แล้ว

  **rename = เพิ่ม + copy + ลบ (2 รอบ) ไม่ใช่ rename รอบเดียว**
- บังคับ required ใหม่ → รับแบบ optional ก่อน, backfill, ค่อยบังคับรอบหน้า

## Rollback ต้องเป็น "ย้อนโค้ดอย่างเดียว"
ถ้า rollback แล้วต้อง**ย้อน state ด้วย** = การเปลี่ยนแปลงนั้นละเมิดกฎข้างบน
(state ที่มีข้อมูลจริงแล้ว มัก**ย้อนไม่ได้จริง** — อย่าออกแบบโดยหวังว่าจะย้อนได้)

## กับดักที่ทำให้ลำดับ "สำคัญ" โดยไม่ตั้งใจ
- **โค้ดใหม่พึ่งของที่ยังไม่มีจริง** — ถ้าโค้ดเรียกสิ่งที่ต้องถูกสร้างก่อน มันคือ *dependency*
  ไม่ใช่ *"แค่ยังไม่ได้ทำ"*; ก่อนปล่อย ให้ไล่ว่า **โค้ดใหม่เรียกอะไรที่ยังไม่ถูกสร้าง**
- **ชุดการเปลี่ยนแปลงที่มีทั้ง "ของที่ต้องมาก่อน" และ "ของที่ต้องมาทีหลัง" ปนกัน** →
  แยกตาม **ทิศทางของ dependency ไม่ใช่ตามหัวข้อ** — ปนไว้ด้วยกัน = deploy ไม่ได้ทั้งสองทาง
- **สร้างสิ่งใหม่แล้วไม่ทดสอบ "การใช้งานจริง" ของมัน** — สร้างสำเร็จ ≠ ใช้งานได้
  (ทดสอบด้วย action จริงที่ระบบจะทำกับมัน ไม่ใช่แค่เช็คว่ามันมีอยู่)

## บังคับด้วยระบบ ไม่ใช่ความจำ
**กฎที่พึ่งความจำ = กฎที่จะถูกละเมิด**
- การเปลี่ยนแปลงชนิดทำลาย (ลบ/rename/บังคับ required) → ให้ CI หรือ review **สะดุด**
  ต้องมีแผนแบ่งรอบก่อนผ่าน
- **precondition ไม่ครบแล้ว "ข้ามเงียบ" = ญาติของ `catch {}`** — ต้อง **fail loud**
  (ส่งของที่พังเงียบขึ้น production แย่กว่าหยุด deploy เสมอ)

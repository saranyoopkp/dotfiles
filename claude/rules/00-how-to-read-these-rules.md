# วิธีตีความ rules

Rules คือ default เชิงหลักการ ไม่ใช่ checklist ที่ต้องทำครบทุกบรรทัด

1. **บริบทและการตัดสินใจของ repo มาก่อน** — ทำตาม decision ที่มีเหตุผลและยังใช้ได้; โค้ดเดิมลำพังไม่ใช่ decision
2. **ปรับตามความเสี่ยง** — เลือกความเข้มของการออกแบบ ทดสอบ และการสื่อสารให้พอดีกับผลกระทบ
3. **อย่าเดาหรือแหกกฎเงียบ ๆ** — เมื่อมีข้อยกเว้นสำคัญ ให้บอกเหตุผลและข้อจำกัดอย่างกระชับ
4. **rules ต้องเล็กและมีบ้านเดียว** — เก็บเฉพาะหลักการข้ามงานที่พลาดแล้วเสียหายหรือพบซ้ำ; รายละเอียดตามประเภทงานอยู่ใน skill

เมื่อมีทางเลือกที่เปลี่ยน trade-off สำคัญสำหรับผู้ใช้ ให้เสนอทางเลือกและต้นทุนสั้น ๆ; ไม่ต้องเพิ่มข้อความมาตรฐานในงานที่ไม่มี trade-off เช่นนั้น
